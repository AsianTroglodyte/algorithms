** Why
What do these properties actually do?

The longest path (root to farthest NIL) is no more than twice the length of the
   shortest path (root to nearest NIL)
    - Shortest possible path: all black nodes
    - longest possibl path: alternating red and black
(show examples AGAIN) be very deliberate. we can start to see why red and black
colors are important.

Then show the lemma. and the not so formal proof.

*lemma* The important lemma says:
 - h <= 2 * lg(n+1)

The intuition is just two facts.

First, black-height grows slowly compared with the number of nodes. If every
path below a node must contain (k) black nodes, the tree needs at least

2^k-1

internal nodes. Each extra black level forces another layer of branching.

Second, the tree cannot have too many red nodes between black nodes. Since red
nodes cannot have red children, the longest path can alternate:

B - R - B - R - B

but never:

B - R - R - B

So the actual height is at most about twice the black-height:

h <= 2bh(root)

Now combine them:

n <= 2^{bh(root)}-1

and since

bh(root) >= h/2

we get:

n >= 2^{h/2}-1

Then just rearrange:

 - n+1 >= 2^{h/2}
 - lg(n+1) >= h/2
 - 2lg(n+1) >= h
 - h <= 2 * lg(n+1)

since a lot of operation such as search, max, min, etc take time propoprtional to height

runtime(n) = c*(2 * lg(n+1))

as you might expect this boils down to a time complexity of:
 - runtime(n) = O(lg(n))

The equal-black-height rule forces enough branching, and the no-red-red rule
prevents paths from stretching too much. Together, they force logarithmic
height.

But why? these specific properties they seem to work, but why do this and not
just balance it *more explicitly*.

We want a search tree to stay short, because its operations depend on height. A
naive solution would be to keep the tree perfectly balanced after every
insertion or deletion, but maintaining such a strict shape could require too
much restructuring. for an algorithm like DSW the time complexity is big theta
of (n). definitely worse than lg(n). Red-black trees use a weaker set of
invariants instead. Those properties/invariants are strong enough to guarantee
height \(O(\log n)\), but simple enough that insertions and deletions can
restore them efficiently using local recoloring and rotations.

Basically, red-black trees do not try to maintain the best possible shape. They
maintain just enough balance to guarantee (O(\lg n)) height while keeping
updates very efficient. Generally speaking the stricter the balancing the
greater the runtime (though it might not necessarily change the asymptotic
runtime).

* Rotations
 1. alters the structure of a tree by rearranging the subtrees
 2. goal is to decrease the height of the tree
    - red-black trees: max height of O(log n)
    - larger subtrees up, smaller subtrees down
 3. does not affect the order of elements; "for a given node, all values in left
    subtrees are still smaller than that node. all values in its right subtree
    are will remain larger."

* The empirical results and analysis
The key column is comparisons/(n log2 n). Because it stays roughly
constant as the number of nodes grows, the total insertion work scales
like \(n\log n\), meaning each insertion averages \(O(\log n)\). Random
insertion performs best, while ascending, descending, and duplicate inputs
require more comparisons, but the red-black tree remains balanced.

The insertion and deletion times increase as the tree grows, but timing
can vary due to Python and system overhead. The three passing tests
confirm that the tested trees maintain logarithmic height, insertion
comparisons stay within an \(O(n\log n)\) bound, and all nodes can be
deleted successfully.


** does this line up with the theory
 Red-black trees guarantee:
- Search: \(O(\log n)\)
- Single insertion: \(O(\log n)\)
- Single deletion: \(O(\log n)\)
- Building or deleting an entire \(n\)-node tree: \(O(n\log n)\)
